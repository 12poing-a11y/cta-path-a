三个单元（均为 A1000k、Base 成本、完整模式、2026-01-05 → 2026-11-25）：
- **A** = 本地快照 / 日历前月开盘价（冻结 E1000k）：99 笔（含窗口末 1 笔未平仓共 100 行）

- **C** = 本地快照 / 主力开盘价：97 笔（共 98 行）——用来分开"成交口径"这一因素

## 1. 结论（一句话）

**多出来的交易，主要来自 B 的行情条上没有 delivery（交割）标记，所以"成交时质量门"没有拦下任何一笔；A 的质量门拦下 122 次入场，其中 52 笔对应的信号在 B 里被成交了。** 信号本身两边逐日一致；席位、升贴水数据两边逐格相同；没有发现"数据静默缺失后放行"的 bug，但有三处**设计层面的口径差异 / 疑点**（§4），需要你裁定。

| 共同（品种、方向、入场日相同） | 71 |

**只在 B 的 68 笔，在 A 里被谁拦下**（逐笔见 `TRADES138_LIST.md`）：

即 **52/68 是质量门**，其余 16 笔是持仓路径不同造成的连锁（A 因被质量门拦下而占用 / 空出仓位的时间与 B 不同）。反方向：只在 A 的 29 笔，在 B 中是路径连锁（13 未评估、13 组合帽未入选、3 满仓），没有一笔是 B 的过滤拦下。

**信号层完全一致**：A、B 都评估过的（日, 品种）里，状态一致的有 无信号→无信号 3,659、可入场→可入场 821、被过滤→被过滤 417、手数为 0→手数为 0 19；不一致的只有 19 个（18 个是 A 当日未评估——已持有或无该品种当日 bar；1 个是 A 可入场而 B 手数为 0）。所以 138 对 99 **不是信号或过滤口径不同，而是成交环节与持仓路径**。

## 3. 机制（为什么 A 拦、B 不拦）

- 质量门 = `entry_fill_allowed` → `tradability_mask`：成交日的 bar 带 `delivery_restricted` / `near_delivery` / `roll_blocked` 任一标记即拒绝入场（`quality:VALID_ONLY`）。这些标记由 `prepare_pack_for_execution` 的日历叠加（`annotate_bars_with_calendar`）**按"日历前月合约"离最后交易日的距离**盖在 bar 上。
- A 是在日历前月合约上成交，所以这个门对它是对的：前月合约临近交割就不开仓。
- B 是在**主力合约**上成交（`skip_contract_overlay`），没有做日历标记：B 的行情条上被标记的 bar 数 = **0**（A、C 各 1,548）。
- 反过来检验这个门对 B 是否本该存在：用同一套日历规则，对 B 的 139 笔入场、A 的 100 笔入场的**实际成交主力合约**计算禁入窗口，**0 笔**落在窗口内。也就是说，**主力合约上成交时，A 的门拦下的那些日子本来就不该被拦**——B 没有"漏拦"，而是门的对象（日历前月合约）与 B 实际成交的合约不是同一个。
- **C 为什么还是 97 笔**：本地快照的 bar 上早就带着日历标记；我的桥接把 `contract_*` 字段去掉了，但**没去掉 `delivery_restricted` 等标记**，所以 C 仍有 123 次质量门拦截。结论：A.5.1 桥接里"成交口径"那一行（本地 / 主力开盘 / 完整，+4.92/+3.21）**没有真正去掉这个门，是不干净的单因素**；官方 / 主力开盘单元才第一次真的去掉。这也解释了 A.5.1 里那个 +13.2/+9.4 的"数据源 × 成交口径交互"：它不是数据交互，是**质量门被一起去掉**。该更正只改变 A.5.1 的归因说法，**不改变任何判定**。

## 4. 完整模式的席位 / 升贴水数据核查

| 检查 | 结果 |
|---|---|
| 席位数据 A 与 B 逐格比较（2026 年，4,821 格） | **0 处不同** |
| 升贴水数据 A 与 B 逐格比较（5,832 格） | **0 处不同** |
| 入场时席位行缺失但未被"席位数据不足"规则跳过 | A、B 各 **0 笔**（没有静默缺失） |
| 入场时升贴水数对缺失 | A、B 各 **0 笔** |
| 席位过滤被跳过的交易（席位数据不足 60 个交易日，按设计放行） | A 35/100，B 41/139；只在 B 的 68 笔里 15 笔 |

- 席位按**品种 × 日期**存储，不涉及合约代码，所以不存在"和官方主力合约对不上"的问题。**大商所 10 个品种的席位数据从 2026-06-02 才开始**（其余 17 个从 2025-10-10），到约 2026-08 底才满 60 个交易日，之前这 10 个品种的席位过滤按设计（fix3 覆盖率闸）被跳过并放行——记录在输出的 `seat_gate.skipped_seat_filter_signals` 和标签「缺席位」里，**不是静默**，但它意味着完整模式在窗口前大半段对大商所品种实质上没有席位过滤。
- **升贴水对不是"官方主力 vs 次主力"**。升贴水来自新浪各合约收盘价，取"在 `public_curve.MONTHS` 主力交割月表里、距到期最近的两个合约"的收盘价（对应前一交易日，可用性滞后 1）。与官方逐合约数据比对（2026 年 5,805 个有效对）：
  - 近端合约 = 官方距到期最近的在市合约：3,522（61%）；
  - 一对价格里**包含官方主力合约**：4,407（76%）；
  - 因升贴水被禁开的 140 次里，**98 次（70%）**的对里含官方主力，**42 次（30%）不含**（例：M 2026-08-26，对为 M2609 / M2611，官方主力是 M2701；PP / EG / L 在 2026-06 ~ 07 的"贴水极端禁开空"，近端是 2609 而官方最近在市是 2607）。
  - 这套对在 A、B 里**逐格相同**，所以不是 138 与 99 之差的原因。
- 因此：**没有发现静默缺失后放行**；但升贴水对的合约选择与官方主力口径不一致：`MONTHS` 表只是各品种的主力交割月子集（例：RB 只有 1/5/10 月、CF 只有 1/5/9 月，而官方在市合约有更多月份，如 RB2607、CF2703），注释却写的是"实际上市的交割月"。

## 5. 三处需要你裁定的点（**都没有确认是 bug，所以没有开 issue，没有修任何代码**）

1. **`near_delivery`（距最后交易日 6–10 个交易日）也在拦入场。** 日历规则里 `no_new_position_sessions = 5`（禁入）、`roll_warn_sessions = 10`（名字是"预警"），但 `tradability_mask` 把 `near_delivery` 与 `delivery_restricted` 一样当成拒绝理由。A 的 122 次拦截里有 36 次只因 `near_delivery`；只在 B 的 52 笔里有 17 笔属此类。规格里没有写明预警窗口是否该禁入，所以我不把它判为 bug；如果你认为"只禁 5 个交易日"才是意图，这就是一个 bug，我再开 issue。
2. **升贴水对与官方主力不对齐**（见 §4，30% 的升贴水禁开来自不含官方主力的对；`MONTHS` 表只含主力交割月、注释却写"实际上市月份"）。这是冻结输入的定义问题，不是代码出错；两边相同，不影响 138 的解释。
3. **长样本引擎（官方 / 主力 / 基础）没有 delivery / 禁入类的成交质量门**（行情条上没有任何标记）。按上面的检验，对主力合约成交它本来不会拦下什么（0/139），所以我也不判为 bug；但这意味着 216 天的冻结 E1000k（日历前月 + 质量门）与长样本引擎的成交环节**不是同一套规则**，A.5.1 的"桥接"在这一点上被我做得不干净（见 §3 最后一条）。

## 6. 核实边界

- 只比较了成交 / 过滤路径，没有比较收益，没有调参；所有数字不计入 DSR。
- 窗口只有 216 个交易日；"路径不同"的 16 笔和只在 A 的 29 笔是持仓占用的连锁，没有逐笔追到最初的分叉点（最初的分叉点是质量门拦下的交易）。
- 升贴水的合约识别按"收盘价与官方合约逐位相等"做，识别率 5,767/5,805（99%）；未识别的是新浪与官方收盘价不同的少数日。
